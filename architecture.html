Where the traffic actually goes

The single most useful fact about this system: Vercel and Supabase never talk to each other. The browser talks to both, separately. Almost every wrong assumption about this app — a phantom second database, an unused /api mirror, a login that broke for a week — traces back to imagining a link between them that has never existed.

01 — Topology

Two independent systems, one browser

Vercel serves files. Supabase runs code and holds data. The browser is the only thing that touches both, and it reaches them over two completely separate connections.

The one constant that wires it together

The browser knows where the backend is because of a single hard-coded line in index.html. There is no environment variable, no build step, no service discovery:

const FUNCTIONS_BASE = 'https://hbiquvmldtoinqtmbvgd.supabase.co/functions/v1'

02 — Division of labour

What each side is responsible for

Vercel

Serves the file, then stops

Ships index.html, sw.js, the manifest and images from a CDN, and sets security headers from vercel.json. That is the entire job.

There is no build step, no framework, and no api/ folder. Every environment variable it once held has been removed, because nothing runs there to read one.

Supabase

Runs everything that thinks

Eleven Deno Edge Functions authenticate each request, enforce ownership, and query PostgreSQL using the service-role key — which never leaves the server.

It also holds the database, the scheduled jobs, and every secret the system needs: the Gemini key, the push-notification keys, the cron secret.

Why this trips people up

Because Vercel hosts the site, it is natural to assume Vercel is the backend. It isn't. That assumption produced a parallel api/ folder of serverless functions that mirrored every endpoint, sat unused for months, and quietly offered a second unguarded door into the same database. It has since been deleted and blocked in .vercelignore.

03 — Request lifecycle

From password to data

Authentication is custom — no Supabase Auth, no JWTs, no third-party provider. A session is an opaque 64-character token in a database table.

Token shape
64 hex characters — 32 bytes from crypto.getRandomValues()
Stored at
localStorage['pwt_token'] in the browser, sessions table on the server
Lifetime
30 days; expired rows deleted on use, plus an hourly sweep
Not used
Cookies, JWTs, Supabase Auth, refresh tokens
04 — Endpoint reference

All eleven functions

Each directory under supabase/functions/ becomes one function, served at {FUNCTIONS_BASE}/<name>. Every one answers OPTIONS for CORS preflight before anything else.

EndpointMethodsWho may call itWhat it does
/auth GETPOSTDEL public to log in Log in, check the current session, log out. The only endpoint reachable without a token.
/leads GETPOSTDEL session The sales pipeline. Engineers see their own; admins see everyone's.
/clients GETPOSTDEL session Won customers, returned with product counts and low-stock totals.
/products GETPOSTDEL session Equipment installed at a client — boilers, cooling towers, chillers, pools.
/activities GETPOST session The follow-up log. One row per call or visit, hanging off a lead or a client.
/convert POST session Turns a “Closed Won” lead into a client, carrying its follow-up history across.
/engineers GETPOSTDEL admin only Team management. Delete is a soft disable; you cannot disable yourself.
/extract POST session Sends text, a photo or a voice note to Gemini and returns structured lead fields.
/subscribe POSTDEL session Registers this browser for push notifications.
/notify POST cron / service key Not called by the browser. Sends due-date reminders — see the scheduled work below.
/location GETPOST admin reads Engineer positions for the admin map. GPS tracking is currently switched off in the app.
Two guards worth knowing about

CORS. Because the browser calls Supabase cross-origin, each function echoes an Access-Control-Allow-Origin only for an allow-listed host — pwt-sales.vercel.app and preview URLs. This list lives in _shared/cors.ts, which is bundled into every function, so deploying only some of them splits the policy and breaks logins on whichever hosts fall out.

The JWT gate. Supabase can verify a JWT before your code runs. This app sends its own opaque token, which is not a JWT — so the gate must stay off. It is pinned per-function as verify_jwt = false in supabase/config.toml.

05 — Data model

Nine tables

Why the table is called “activities”, not “lead_activities”

Because it holds follow-ups for clients too. The database used to call leads sites — a fossil from when the app was a site-survey tool called SiteTrack — and that mismatch between the screen and the schema caused steady confusion until the whole data layer was renamed in August 2026.

06 — Deployment

Two pipelines that do not know about each other

This is the second thing that catches people out. Pushing to git deploys the website. It does not deploy the backend.

The failure this causes

Change a function, push to git, and the website updates while the backend stays on the old code. If the frontend now calls an endpoint that hasn't been deployed, the app breaks for everyone until you run the Supabase deploy. When both must change, deploy the database first, then the functions, then push the frontend.

Scheduled work

One job runs without anyone touching it: pg_cron inside PostgreSQL calls /notify every hour, which finds leads due within twelve hours and sends a push notification to the engineer who owns them. A second job clears the notification log nightly. Neither involves Vercel.

07 — How access is controlled

Three layers, all server-side

Layer 1 · the function

Session and ownership

Every protected endpoint validates the bearer token, then filters by owner: an engineer sees only their own records; an admin sees all. Mutations re-check ownership before writing, and reject with 403.

Layer 2 · the database

Row Level Security

Every table carries a service_role_only policy. Even with a valid Supabase API key, a direct request to the database returns nothing — only the service-role key held inside the Edge Functions can read a row.

Layer 3 · the browser never holds a database key

There is no Supabase client library in the frontend and no API key in the bundle. The only credential the browser ever holds is its own session token, which is useless anywhere except these eleven endpoints. That is why the hard-coded FUNCTIONS_BASE URL is safe to have in plain sight.

The thing to fix first

The Supabase project runs on the Free plan, which includes no database backups at all. Nothing else on this page can lose your data; that can. Either move to the Pro plan for scheduled backups, or export the tables to CSV on a regular schedule.
